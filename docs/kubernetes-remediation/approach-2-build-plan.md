## Model & provider

- The main Claude Agent SDK session is the Claude Opus orchestrator. Project agent definitions run `remediation-investigator` and `remediation-verifier` on DeepSeek 4.1 Flash at `xhigh`, with Opus as fallback. Opus reviews every delegated result; this is not a DeepSeek-only orchestrator.
- Opus must use the user's Claude subscription through a gateway-returned OAuth consent URL. The container receives only `ANTHROPIC_AUTH_TOKEN=gateway-managed`; no `ANTHROPIC_API_KEY`, OAuth token, or static Claude secret enters the container or cluster. The gateway must store and refresh the subscription credential host-side.
- **OAuth verification: unsupported in the installed wiring.** `GatewayConnectionResult` can represent `action: 'oauth'` (`src/gateway-providers/gateway-provider-registry.ts:116`), but OneCLI's adapter returns only `operator_console` or `unsupported` (`src/gateway-providers/onecli.ts:235-251`). OneCLI 2.2.5 has no Claude provider or Claude subscription-login command. Do not deploy until `pnpm ncl groups connect --id <GROUP_ID> --host api.anthropic.com` returns `action: oauth` with a real `connect_url`, and a subscription-authenticated Opus request proves refresh works without a static API key.
- DeepSeek stays gateway-managed under the existing `claude-deepseek` key. Treat `/home/jopdorp/.config/deepseek/key` only as the operator-side import source: never print it, mount it, copy it into `container.json`, or place its value in an environment variable.
- **Open routing gap:** the SDK supports the requested per-agent model, effort, and fallback settings, but the installed gateway has not proved it can route Opus subscription traffic and `deepseek-flash` traffic from one SDK session to separate upstream credentials. That dual-route proof is a deployment blocker.

## RBAC artifact and hard-limit proof

`home-k3s-rbac.yaml` contains the dedicated namespace and ServiceAccount, a minimal cluster-scoped read role, per-namespace read Roles/bindings, Lane A Roles/bindings, the name-scoped Lane B Role, and unbound human-approved PV/PVC deletion capabilities. `admission-policy.yaml` is the mandatory fail-closed field guard.

| Contract                  | Enforcement in the manifest                                                                                                                                                                                                                                                                    |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No Secret reads           | `secrets` is absent from every rule; there are no wildcard API groups/resources/verbs.                                                                                                                                                                                                         |
| No self-escalation        | No write verb exists for ServiceAccounts, Roles, RoleBindings, ClusterRoles, ClusterRoleBindings, namespaces, token requests, impersonation, bind, or escalate. No writer RoleBinding exists in `nanoclaw-remediator`.                                                                         |
| Namespaced read isolation | The ClusterRole reads only Nodes, PVs, StorageClasses, CRDs, and ClusterVulnerabilityReports. All namespaced reads use Roles bound only in approved namespaces; VulnerabilityReports remain readable in every namespace where live reports exist.                                              |
| No own Deployment change  | The bot remains host-run and `nanoclaw-remediator` has no workload writer binding. Future in-cluster components must stay there.                                                                                                                                                               |
| No exposure/DNS change    | Services, Endpoints, EndpointSlices, Ingresses, IngressClasses, NetworkPolicies, and ConfigMaps have read verbs only. No write to CoreDNS or Service objects means no `LoadBalancer` mutation.                                                                                                 |
| Lane C read-only          | Only namespace-scoped read bindings reach those namespaces; no Lane A/B RoleBinding does.                                                                                                                                                                                                      |
| No backup mutation        | All Longhorn resources, including `backups` and `backupvolumes`, have read verbs only; snapshot APIs receive no write rule.                                                                                                                                                                    |
| Lane A operations         | Only `patch` on Deployments/StatefulSets/DaemonSets and `get/patch` on Deployment/StatefulSet scale are granted in the sixteen reviewed namespaces. No storage delete is autonomous.                                                                                                         |
| Always-ask operations     | Only name-scoped workload patch for Vaultwarden/WireGuard and unbound reviewed storage-delete roles; no scale or self-heal grant.                                                                                                                                                            |
| PV/PVC deletion           | Separate roles are labeled as requiring per-action human approval and have no binding. The proxy must validate a once-only Matrix approval, stamp the approval annotation with its own identity, install only the short-lived binding needed for that action, delete, then remove the binding. |

Important: RBAC authorizes a resource and verb, not patch fields. `admission-policy.yaml` therefore targets the remediator ServiceAccount and fail-closes every workload/scale update except digest-pinned same-repository images, the restart annotation, or replicas from 0 through 10. It separately pins Vaultwarden to `docker.io/vaultwarden/server@sha256:<64 lowercase hex>` and gates storage deletes on the proxy-owned approval annotation. The proxy and admission policies are mandatory go-live controls.

## Build sequence

1. Keep the host and Docker runtime unchanged. Reuse `src/drivers/types.ts:300` and `src/drivers/docker-driver.ts:68`; do not add a Kubernetes session driver. Approach 1 can later reuse these Roles/bindings and replace only the runtime/credential transport.
2. Add `src/modules/kubernetes-remediation/` and import it from `src/modules/index.ts:19`. Keep four small seams: `policy.ts` (pure allow/deny), `ingest.ts` (Trivy/Falco normalization and dedupe), `approval.ts` (canonical plan plus approval registration), and `executor.ts` (exact patch, observation, bounded recovery). Add one SQLite migration for incident fingerprint, immutable plan, approval/execution state, target UID/resourceVersion, attempt count, and deadline.
3. Do not mount `/home/jopdorp/.kube/mini-pc.fresh` or a bearer-token kubeconfig. Generate a dedicated, read-only kubeconfig whose API server is a host policy proxy; mount it through `buildMounts` at `src/container-runner.ts:1069` after extending the typed mount policy in `src/drivers/types.ts:28`. The proxy alone holds a short-lived TokenRequest credential for `nanoclaw-remediator`, never the admin kubeconfig; the agent sees only a per-session proxy identity.
4. The proxy forwards the explicit read surface. It rejects every write unless it matches a live, once-only approved plan byte-for-byte: target namespace/kind/name/UID/resourceVersion, allowed JSON paths, and expiry. Lane A permits only container/initContainer image values, `kubectl.kubernetes.io/restartedAt`, or the scale subresource. Lane B permits only `docker.io/vaultwarden/server@sha256:[0-9a-f]{64}` on the existing container image field. PV/PVC deletion is never self-heal: after a fresh Matrix approval, the proxy stamps `remediation.nanoclaw.io/approval-id`, creates the narrowly scoped temporary binding under an operator identity, deletes through the remediator identity, consumes the grant, and removes the binding. `admission-policy.yaml` independently enforces the workload, scale, and delete gates and fails closed.
5. Trivy uses a small host watcher, not a webhook: watch `vulnerabilityreports.aquasecurity.github.io` and `clustervulnerabilityreports.aquasecurity.github.io` with bookmarks, re-list on HTTP 410, and dedupe by report UID/resourceVersion plus vulnerability/image digest. Live reports currently exist in `cert-manager`, `gitea`, `kube-system`, `openclaw-private`, and `wireguard-home`, plus cluster-scoped reports. Resolve report owner references to the workload using the read role, then enqueue only changed actionable findings.
6. Falco uses Falcosidekick's custom webhook because Falco alerts are not Kubernetes Events. A human later points Falcosidekick at a new `registerWebhookHandler` route (`src/webhook-server.ts:107`); the handler must authenticate an HMAC/bearer value, cap body size, rate-limit, and return before agent work. The current raw-route server binds `0.0.0.0` at `src/webhook-server.ts:188` and supplies no authentication itself. Normalize and dedupe Falco alerts before waking the remediation session.
7. Feed normalized incidents into one dedicated agent-group session through the existing mailbox/wake path (`src/session-manager.ts:255`). The agent may read and propose, but it cannot create an executable grant. Its proposal is a typed plan containing lane, incident IDs, exact target identity, precondition resourceVersion, before/after image or replicas, health deadline, and rollback value.
8. Register action `kubernetes_remediation` with `requestApproval`/`registerApprovalHandler` (`src/modules/approvals/primitive.ts:216`). Show namespace, kind/name, current image, proposed digest, vulnerability/Falco reason, exact allowed fields, rollback, and expiry in the Matrix DM. Use this approval primitive rather than generic `ask_user_question`: it binds the DM recipient at `src/modules/approvals/primitive.ts:255`, authorizes the click at `src/modules/approvals/response-handler.ts:127`, and atomically transitions once at `src/modules/approvals/response-handler.ts:79`.
9. On Approve, the host handler re-gets the target, rejects UID/resourceVersion or current-value drift, re-runs `policy.ts`, opens one once-only proxy grant, applies the exact patch, and records the API response and rollout result. Reject/expiry performs no cluster call. Vaultwarden always requires a fresh card with the full official digest and never enters recovery.
10. Implement Lane A self-heal as a host state machine, not an agent loop: one target tuple `(namespace, kind, name, UID)`, ten-minute wall clock, and at most two automatic writes after the approved change. For an image rollout: one restart, then one rollback to the recorded prior image; for scale: one rollback to prior replicas; for a restart: one retry only. Every write uses a fresh resourceVersion precondition. Any cross-workload/cross-namespace action, exhausted cap, policy denial, target drift, or continuing unready state closes the grant and sends a new Matrix escalation. Lanes B/C have zero self-heal attempts.
11. Matrix remains an install step, not assumed trunk capability: `.claude/skills/add-matrix/SKILL.md:8` says the adapter is copied from the `channels` branch, and real homeserver delivery is still manual at line 83. First add its pinned adapter/patch, then verify registration, authorized button clicks, edited terminal cards, restart recovery, and a real Element DM before enabling any write grant.
12. Tests before human deployment: table-test every policy allow/deny and JSON-path diff; approval replay/expiry/unauthorized click; target drift; watcher reconnect/dedupe; Falco auth/body/rate limits; caps and Lane B/C zero-recovery. In an ephemeral k3s cluster, compile/apply the RBAC and admission policies, then run a positive/negative `kubectl auth can-i` matrix and adversarial patches (env/envFrom, volumes/mounts, ServiceAccount, security context, host namespaces/ports, container reorder, labels/selectors, arbitrary or tag-based images, Vaultwarden wrong repository, replicas outside 0..10, Secret/RBAC/Ingress/Service writes, storage delete without a live approval). Never use HOME for these tests.

## Pod Security Admission

The empty `nanoclaw-remediator` namespace is labeled `restricted` enforce/audit/warn at version `v1.35`. Read-only inspection of live pod specs found that every approved workload namespace currently fails `restricted`, so none receives an enforce label yet: `bitcoind`, `excalidraw-room`, `gitea`, `logging`, `mail`, `monitoring`, `nextcloud`, `openclaw-private`, `wiki-js`, `vaultwarden`, `cert-manager`, `falco`, `kube-system`, `longhorn-system`, and `wireguard-home`. All have at least privilege-escalation or seccomp gaps; the infrastructure and runner/logging namespaces also use privileged containers, hostPath, host namespaces, or added host capabilities. Harden ordinary workloads first; retain explicit, documented exceptions for components whose node access is intrinsic.

## Top five risks / unknowns

1. The CEL must compile and the full positive/negative matrix must pass in ephemeral k3s; neither RBAC nor admission has been applied to HOME.
2. Credential delivery is not solved by a read-only mount: any raw SA token visible to the agent is replayable, so token minting/storage/rotation must remain host-side behind the policy proxy.
3. Matrix is not trunk-installed and its real homeserver/card/restart behavior is only manually verified; no approval-dependent write should ship before that E2E test.
4. Falcosidekick webhook authentication/header support and burst behavior need validation against the installed `2.32.0`; otherwise place an authenticating, rate-limiting reverse proxy in front.
5. Namespace classification and the PV `resourceNames` snapshot will drift; `excalidraw` already contradicts the audit premise. New namespaces/PVs remain inaccessible until review, and stale PV names must never be auto-expanded from agent output.
